BMCyber складається зі служби systemd, що працює від root на одному хості,
та локального клієнта дії Fail2ban. Детектор надмірного потоку запитів MyCount
залишається в MyCount. Інтеграція зі SnakeWeb виходить за межі цієї реалізації.

## Передумови {#prerequisites}

Потрібні Linux із systemd, набори nftables із часом дії елементів, Fail2ban
і Python 3.11 або новіший. PyZMQ має бути доступний для `/usr/bin/python3`;
перевірену версію зазначено в `requirements.txt`. Інсталятор перевіряє
залежності, але не встановлює системні пакети чи залежності Python. Він явно
використовує `/usr/sbin/nft`. Інсталятору також мають бути доступні `groupadd`,
`systemctl` і `fail2ban-client`. Виконуйте команди життєвого циклу з окремої
робочої копії вихідного коду.

Перевірено: Python 3.13.5, PyZMQ 26.4.0/libzmq 4.3.5, nftables 1.1.3,
Fail2ban 1.1.0 і Linux 6.12.111+deb13-amd64. Перед розгортанням перевірте
поведінку штатних інструментів на версіях, установлених на wintermute.

## Встановлення, оновлення та видалення {#install-upgrade-and-uninstall}

Ці команди призначені для оператора; розробка й тести не виконують
встановлення на хості автоматично.

```sh
sudo scripts/install.sh --check
sudo scripts/install.sh
sudo scripts/upgrade.sh --check
sudo scripts/upgrade.sh
sudo scripts/uninstall.sh --check
sudo scripts/uninstall.sh
```

Усі три сценарії підтримують `--help`. Режим `--check` виконує перевірку без
зміни файлів, облікових записів, служб або правил; попередня перевірка nftables
усе одно потребує прав на перегляд і перевірку брандмауера. Некоректна
конфігурація або відсутні залежності спричиняють помилку до зупинки служб.

Під час встановлення вихідний код застосунку копіюється до `/opt/prod/bmcyber`,
створюється системна група `bmcyber`, якщо її ще немає, записуються лише
визначені файли служби, фільтра, дії та jail. BMCyber запускається перед
завантаженням свого jail. Служба працює від **root**, а не від окремого
облікового запису. Користувач `bmcyber` не створюється. systemd створює
`/run/bmcyber` із власником і групою `root:bmcyber` та режимом `0750`;
маска процесу `0117` відразу забезпечує режим IPC-сокета `0660`.
Блокування, що належить root, не дає другому екземпляру служби замінити сокет.
Застарілі сокети видаляються лише після отримання цього блокування;
сторонні файли відхиляються.

Інсталятор відмовляється перезаписувати ресурси, які не належать застосунку.
Оновлення й повторне встановлення зберігають JSON робочого середовища, дані
оператора та розгорнутий jail MyCount. Значення `.deployment-version`
оновлюється лише після запуску служби й успішної штатної перевірки
працездатності через IPC. Невдале розгортання повідомляє про помилку;
копіювання файлів не забезпечує транзакційного відкочування. Після помилки
перевірте робочу копію або повторіть операцію.

Видалення прибирає належні застосунку файли служби, фільтра, дії, jail,
вихідний код і таблицю nftables. Воно зберігає сторонні таблиці брандмауера
та jail Fail2ban, JSON робочого середовища, дані користувача й копію jail
MyCount у `conf/bmcyber-mycount.local`. Системна група та її учасники
залишаються. Маніфест належності ресурсів враховує збережені файли й дозволяє
повторне видалення або встановлення. Під час видалення позначка останньої
успішно встановленої версії прибирається.

## Налаштування та керування {#configure-and-operate}

Файл конфігурації робочого середовища — `/opt/prod/bmcyber/conf/bmcyber.json`.
Відсутні поля успадковують типові значення констант; некоректні файли,
невідомі параметри, хибні типи та недопустимі значення спричиняють явну
помилку. Під час першого встановлення файл створюється з констант лише за
його відсутності. Явно задані значення є перевизначеннями оператора й
залишаються незмінними, навіть якщо типові значення згодом зміняться.
Після редагування перезапустіть службу.

| Параметр JSON | Константа типового значення | Типове значення та перевірка |
| --- | --- | --- |
| `ipc.socket_path` | `DZMQ.SOCKET_PATH` | `/run/bmcyber/control.sock`; іменований сокет безпосередньо в `/run/bmcyber`, шлях до якого не перевищує обмеження довжини в Linux. |
| `ipc.timeout_seconds` | `DZMQ.TIMEOUT_SECONDS` | `5`; скінченне число від `0.01` до `60`. |
| `ban.base_hours` | `DPolicy.BASE_HOURS` | `20`; скінченне число, що відповідає щонайменше одній секунді. |
| `ban.random_extra_hours` | `DPolicy.RANDOM_EXTRA_HOURS` | `4`; скінченне невід’ємне число. Базова тривалість разом із максимальним додатком не може перевищувати сім діб. |
| `ban.protected_ips` | `DPolicy.PROTECTED` | Мережі зворотного зв’язку IPv4 та IPv6; масив числових адрес або канонічних мереж CIDR. |

Політика визначає тривалість у цілих секундах як базову тривалість плюс
випадковий додаток. Значення `bantime` штатного jail має бути не більшим
за мінімальну тривалість блокування служби. Якщо зменшуєте `base_hours`,
також скоригуйте строк дії запису Fail2ban, щоб він міг виявляти нові
зловживання після завершення блокування в ядрі. Цей штатний інтервал
не видаляє записи блокування.

Перевіряйте конфігурацію та керуйте інтеграцією в явному порядку:

```sh
python3 -m bmcyber --check-config --config conf/bmcyber.json
sudo scripts/services start
sudo scripts/services restart
sudo scripts/services stop
```

Команда запуску спочатку запускає BMCyber, потім Fail2ban, а тоді
перезавантажує визначений jail. Команда зупинки зупиняє лише jail MyCount,
потім BMCyber, залишаючи сторонні jail Fail2ban активними. Перезапуск
перевіряє конфігурацію застосунку та Fail2ban перед зупинкою. Додайте
обліковий запис, від якого працює клієнт дії без прав root, до групи
`bmcyber` і почніть новий сеанс, щоб набуло чинності членство в додатковій
групі.

Установлений клієнт підтримує:

```sh
/opt/prod/bmcyber/scripts/bmcyber-client health
/opt/prod/bmcyber/scripts/bmcyber-client ban --ip 192.0.2.10 --source mycount
```

Команда блокування є прикладом із документаційною адресою. Клієнт також
приймає глобальні параметри `--config`, `--timeout` і `--locale` перед
назвою методу. Він повертає нуль лише після успішного підтвердження,
зіставленого із запитом. Відхилення, відсутність служби й перевищення часу
очікування повертають ненульовий код. Якщо відповіді немає, результат
невизначений: клієнт не повторює запит наосліп і не переходить до прямого
керування брандмауером. Повідомлення клієнта для користувача беруться з
постачуваного англійського каталогу; переклади інтерфейсу клієнта не
постачаються. Діагностичні повідомлення служби надходять до журналу systemd.

## Протокол IPC {#ipc-protocol}

IPC використовує протокол BMForge ZMQ REQ/REP версії `1`: один JSON-кадр
у UTF-8 на запит і відповідь, максимальний розмір кадру — 65 536 байтів.
Конверт повідомлення має такий вигляд:

```json
{
  "protocol_version": 1,
  "sender": "mycount-action",
  "target": "bmcyber",
  "method": "ban",
  "payload": {"ip": "192.0.2.10", "source": "bmcyber-mycount"}
}
```

Метод `ban` приймає лише окрему числову адресу IPv4/IPv6 та діагностичний
ідентифікатор джерела, що відповідає `[A-Za-z0-9][A-Za-z0-9_.-]{0,63}`.
Тривалість, необроблений текст журналу, команда nft, назва таблиці або
заявка на блокування від окремого джерела не приймаються. Метод `health`
приймає порожнє корисне навантаження та виконує обмежену перевірку власних
правил лише для читання. Значення `target` також може бути null.
Непідтримувані методи й адресати повертають помилки.

Відповіді зберігають метод запиту й адресуються початковому відправнику.
Їхнє корисне навантаження містить `status: "ok"` або `status: "error"` із
`error.code` та `error.message`. Успішне блокування повертає нормалізовану
адресу `ip` і вибрану тривалість `duration_seconds`. Коди помилок включають
`invalid_request`, `wrong_target`, `unknown_method`, `enforcement_failed`
та `internal_error`. Некоректні запити, зокрема з непарними сурогатними
кодами Unicode у вкладених даних чи ключах, отримують відповідь із помилкою,
не завершуючи робочий процес. Група IPC визначає межу авторизації клієнтів;
`sender` і `source` є діагностичними рядками, а не підтвердженими
ідентичностями.

## Життєвий цикл брандмауера {#firewall-lifecycle}

BMCyber володіє лише `table inet bmcyber`, позначеною коментарем належності,
двома наборами адрес із часом дії та правилами відкидання вхідного трафіку
з пріоритетом `-10`. Наявна власна структура перевіряється й ніколи не
очищається під час запуску. Інші таблиці брандмауера продовжують
застосовувати свою звичайну політику. Правила стосуються вхідного трафіку
хоста, зокрема до Caddy; вони не налаштовують переспрямований трафік або
трафік контейнерів.

У перевіреній версії nftables 1.1.3 команда `add element` для вже активної
адреси оновлює її час дії. Тому повторний запит застосовує нову повну
тривалість, вибрану службою. Застосунок не зберігає строків завершення
чи обліку дублікатів. Завершення часу дії елемента набору відновлює трафік
без циклу очищення в застосунку. Адаптер також підтримує явне видалення
адміністратором; методу розблокування через IPC немає, і Fail2ban ніколи
не викликає видалення.

Перезапуски служби зберігають активні записи ядра. Перезавантаження хоста
їх втрачає, і BMCyber нічого не відновлює. Відновлені штатні записи
Fail2ban можуть надсилати звичайні нові запити. Стороннє видалення чи зміна
таблиці спричиняє явні помилки перевірки працездатності та блокування;
виправте структуру й перезапустіть службу для повторної ініціалізації.
Не включайте таблицю BMCyber до збереженого набору правил хоста.

## Перевірка {#verification}

Запустіть звичайні тести, які використовують тимчасові IPC-сокети,
тестові файлові системи й служби та не змінюють правила брандмауера:

```sh
python3 -m pytest -q tests
```

У середовищі, що дозволяє простори імен користувачів і мережі, запустіть
перевірку реального брандмауера, установивши захисний параметр на
батьківський простір імен:

```sh
python3 - <<'PY'
import os, subprocess, sys
env = dict(os.environ, BMCYBER_PARENT_NETNS=str(os.stat('/proc/self/ns/net').st_ino))
subprocess.run(['unshare', '-Urn', sys.executable, 'tests/live_firewall.py'], env=env, check=True)
PY
```

`tests/live_fail2ban.py` використовує такий самий захисний параметр і
потребує `BMCYBER_FAIL2BAN_ROOT`, що вказує на розпаковане дерево пакета
Fail2ban. Тест запускає тимчасовий демон із тестовим jail, який опитує
журнал, і скороченими тривалостями; використовує робочий клієнт із
підставленою тимчасовою кінцевою точкою та перевіряє штатне виявлення,
винятки й збереження блокування після завершення строку запису,
ручного розблокування та зупинки jail. Для цього тесту не потрібно
встановлювати пакети чи служби на хості.

`tests/live_permissions.py` потребує root і використовує лише тимчасові
сокети для перевірки дозволеного учасника групи без прав root та
стороннього непривілейованого облікового запису. `tests/live_service.py`
потребує явних захисних параметрів для окремих просторів імен монтувань
і мережі та прав root; він перевіряє справжню точку входу служби з
тимчасовими монтуваннями `/run` і файлу груп. Не запускайте ці тестові
середовища проти встановленої служби.

Виконані перевірки охоплюють штатне відкидання пакетів IPv4/IPv6 та
завершення блокувань, повторне додавання, явне видалення через адаптер,
збереження сторонніх таблиць, запуск, зупинку й перезапуск служби від root,
фактичні групові права IPC, відновлення після некоректних повідомлень,
коди помилок клієнта, перевірку файлу служби systemd, а також належність
ресурсів і поведінку при помилках встановлення, оновлення та видалення
з тестовими службами. Штатна перевірка фільтра знаходить дві очікувані
події IPv4/IPv6 у `tests/fixtures/security-events.log`, розпізнає всі
вісім часових позначок і відхиляє шість нешкідливих або некоректних записів.

Фактичне встановлення під керуванням systemd на wintermute ще не
виконувалося. Перед розгортанням перевірте версії пакетів, справжній шлях
до журналу MyCount, довірену конфігурацію проксі й визначення IP-адреси
клієнта, адміністративні винятки та повну поведінку встановлення,
оновлення й видалення на одноразовому тестовому хості із systemd.
